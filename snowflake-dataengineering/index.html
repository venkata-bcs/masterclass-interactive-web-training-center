01

Snowflake in 60 seconds

In plain English

Snowflake is a database you rent by the second. Your data sits in cheap cloud storage (S3, Azure Blob or Google Cloud Storage). When you want to run a query, you switch on a virtual warehouse, which is a group of compute servers. When it has been idle for a while, it switches itself off and you stop paying. Storage and compute are billed separately, so 50 analysts and 10 ETL jobs can share the same data without slowing each other down.

Layer 1 • The brain
Cloud Services

Logins, security, the query optimizer, transactions and metadata. It is always on and managed by Snowflake.

Layer 2 • The muscle
Virtual Warehouses

Clusters of compute that you start, resize and suspend. They run your queries and loads, and you pay credits only while they run.

Layer 3 • The memory
Database Storage

All table data, compressed into columnar micro-partitions in cloud object storage. Every warehouse reads the same copy.

Warehouse scaling at a glance

  • Resizing (scale up / down): make a warehouse bigger or smaller at any time with ALTER WAREHOUSE … SET WAREHOUSE_SIZE = …. A bigger size speeds up large, slow queries. Queries already running finish on the old size, and new queries use the new one.
  • Multi-cluster scaling (scale out): handles many users at once by adding identical compute clusters. In Auto-scale mode (min < max clusters) Snowflake adds and removes clusters as load changes. In Maximized mode (min = max) all clusters run whenever the warehouse is on. Requires Enterprise Edition or higher.
  • Auto-suspend / auto-resume: an idle warehouse switches itself off after AUTO_SUSPEND seconds and wakes up when the next query arrives, so you stop paying while nothing runs.

Rule of thumb: slow queries → resize; queued queries → add clusters. Try both in the Module 01 simulators →

04

Coming from Oracle, SQL Server or Postgres?

Unlearn these first. Most beginner mistakes come from expecting an OLTP database.
You are used to…In Snowflake
Creating indexes for speedStandard tables have no indexes. Speed comes from pruning micro-partitions, from clustering keys, and from the Search Optimization Service for point lookups.
Primary and foreign keys being enforcedOn standard tables they are informational only. Only NOT NULL is enforced, so duplicates are your pipeline's job. Hybrid tables are the exception.
Running VACUUM / ANALYZE / index rebuildsNone of that exists. Statistics are kept automatically and old micro-partitions are purged by the service.
Sizing a server up frontPick a warehouse size per workload and change it in one SQL statement, in seconds.
Row-by-row inserts in a loopBulk-load files with COPY INTO or Snowpipe. Singleton inserts create tiny micro-partitions and are slow.
Backups with RMAN or pg_dumpTime Travel, zero-copy clones and replication cover most needs, plus a 7-day Fail-safe on permanent tables.
Paying for the server 24×7Compute is billed per second (60-second minimum each time a warehouse starts) only while a warehouse runs.

Set up your practice account (10 minutes)

  1. Sign up for a 30-day trial at signup.snowflake.comChoose Enterprise edition so Time Travel beyond 1 day and multi-cluster warehouses work. Pick the cloud and region closest to you.
  2. Open SnowsightThis is the web UI. Go to Projects → Worksheets and create a SQL worksheet.
  3. Check the shared sample dataTrial accounts usually include the SNOWFLAKE_SAMPLE_DATA database (TPC-H, TPC-DS). The lab generates its own data, so it works without it.
  4. Put a spending guard in placeRun the resource monitor statement below so a forgotten warehouse can never burn your trial credits.
USE ROLE ACCOUNTADMIN;

-- Cap the whole account at 20 credits per month while learning
CREATE OR REPLACE RESOURCE MONITOR learning_cap
  WITH CREDIT_QUOTA = 20
  FREQUENCY = MONTHLY
  START_TIMESTAMP = IMMEDIATELY
  TRIGGERS ON 80 PERCENT DO NOTIFY
           ON 100 PERCENT DO SUSPEND;

ALTER ACCOUNT SET RESOURCE_MONITOR = learning_cap;
