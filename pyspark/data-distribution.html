Module 01b · Interactive guide

Data Distribution & File Splits Explorer

The Spark driver assigns data to workers as partitions: groups of complete rows. This page shows exactly how it gets there, from the Delta Lake / Iceberg file list through the split arithmetic and Parquet row groups to the task each worker receives. Every panel is interactive, and the floating slider controls animation speed.

The driver decides, workers only execute Rows are split, columns are not maxPartitionBytes 128 MB · openCostInBytes 4 MB
01

Rows travel, columns stay together

A DataFrame is split horizontally. Every worker receives complete rows and the full schema. With Parquet, workers only read the columns your query needs from disk.

02

Who decides? The driver's 4-step pipeline

The split is never decided by the worker, and not by Delta Lake or Iceberg either. The table format is the catalog; the Spark driver does the math and hands out byte ranges.

03

Split calculator: from files to tasks

Spark's file-planning algorithm, step by step: the split size formula, cutting files, bin-packing chunks into partitions with the open-cost penalty, then waves of tasks on worker cores.

04

Inside one Parquet file: where the cut really lands

Byte splits are computed without looking inside the file. At read time each task keeps only the row groups whose midpoint falls in its byte range, so no worker reads a partial row group.

05

Column projection: same rows, far fewer bytes

Columns are never split across workers, but because Parquet stores each column separately, a worker fetches only the column chunks the query selects.

06

Tiny files & compaction

A tiny file cannot be split, and thousands of them cost more to open than to read. Compaction rewrites them into well-sized files so the default split engine works at its best.

07

Z-ordering: let workers skip whole files

Clustering similar values into the same files tightens each file's min/max statistics, so the driver can drop files before any task is created.

08

Data skew & salting

After a groupBy or join, rows are routed by key. A heavy key lands on one worker; a random salt spreads it out, and a second aggregation stitches the pieces back together.
